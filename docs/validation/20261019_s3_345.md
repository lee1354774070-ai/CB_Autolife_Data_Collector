## 哪些S3改动有必要

| 改动 | 结论 |
|---|---|
| 从配置的Python获取动态库根路径 | 345标准Conda布局下与旧路径相同；为自定义路径/venv保留。只在启动时执行两次，不增加逐帧开销。 |
| ROS工作空间可选、显式编号/域优先 | 通用兼容，不是S3专属数据分支。不能靠安装空工作空间或硬编码编号取代。 |
| `ROBOT_TYPE`元数据标签 | 保留。区分新S3数据；不变换关节/EEF，不自动重标旧数据。 |
| DAgger S2/S3型号、URDF和控制接口校验 | 保留。涉及物理型号和控制约定，装好Python包不能消除差异。 |
| `s3_thor_preview.py`及其回放工具 | 可选推理工具，不是采集依赖。普通采集不导入、不启动、不占其运行CPU/GPU；删除它不会解决采集同步问题。 |
| 独立S3采集分支/重复采集实现 | 不需要。当前main共用同一关节解析、SHM读取、同步和存储实现。 |

本次不为压缩文件数量删除已有预览能力，也不移除同步/依赖保护；实际更改仅更新过时说明和此记录。

未启用state回退。不能将“没有收到命令”写成全0、保持最后一帧，或声称两种模式相等。

### 原厂App操作期间

两段连续只读监听分别为255.35秒和149.13秒，接收完整状态包25160和14815条（窗口短暂重叠，
不当作不重复帧数相加）。手臂、头、腰和夹爪均有真实变化，两段的以下两个话题始终各0条：

- `/topic_arm_whole_body_target_joints_position_0_345`
- `/topic_arm_gripper_target_joints_position_0_345`

另以可靠QoS交叉监听20秒，状态包2002条，上述两个命令话题仍为0条；类型都是
`std_msgs/msg/String`，其发布端可靠/易失QoS与两次订阅兼容。旁路V4话题在该可靠QoS
探测中不兼容，故不对V4是否发布作结论；本轮验收对象是用户确认的原厂App。
未拿到原厂内部VR控制实现源码，不能据此断言内部具体调用了哪个SDK函数。

同一状态包内的实测值与回报目标示例（各行取自不同采样时刻，单位度）：

| 关节 | observation.state | status_target action | joint action |
|---|---:|---:|---|
| 左肘 | -104.203880 | -101.366188 | 无命令样本 |
| 右肘 | -99.787369 | -112.851463 | 无命令样本 |
| 左夹爪 | 355.603271 | 355.603271 | 无命令样本 |
| 右夹爪 | 358.969727 | 358.969727 | 无命令样本 |

右肘这行的13.064度差是**控制器回报目标与实测位置之差**，不是joint与status_target之差。
夹爪相等是当前解析规则取同一实测值的结果，不证明目标夹爪没有跟踪误差。
两种action模式没有可配对的真实joint样本，不能声称数值相等、给出虚构的joint向量，
或把未收到消息解释为解析出0。

结论：345当前原厂App数据采集使用`ACTION_MODE=status_target`；想使用纯命令标签，
需先有持续发布的身体/夹爪命令输出或经过核实的目标报告接口。安装Python依赖、换Collector
分支或打开state回退并不能补出这些命令。DAgger的独立代理话题不是此次测试对象。

状态包和两路EEF的payload timestamp比本地接收时间落后约19.37秒，代码按现有时钟偏差保护回退到接收时间。
因此当前同步是软件接收时间对齐，不是硬件曝光/控制时刻同步；这不是本次S3合并引入的新规则。

```json
{
  "SET_LEFT_GRIPPER_SPEED": 0.0,
  "SET_LEFT_FORCE": 0.21665826439857483,
  "SET_RIGHT_GRIPPER_SPEED": 36.946659088134766,
  "SET_RIGHT_FORCE": 0.19863836467266083
```

因此不能仅把`ACTION_MODE=joint`的订阅改为`/control_topic_0_345`；它缺少该模式需要的
完整机器人目标关节角和夹爪目标位置。

ROS图确认原厂`node_arm_vr_control_service_0_345`订阅这个输入话题。

对当前Collector而言，已实测可读取的关节目标是状态话题中的
